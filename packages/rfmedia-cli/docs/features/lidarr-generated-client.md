# Lidarr Generated Client

## Decision and Status

Issue #194 replaced the temporary handwritten Lidarr endpoint layer with a complete, private Fetch
SDK generated from a committed official OpenAPI snapshot. Issue #199 extends the required generated
contract for artist profile and tag management, and issue #222 adds search and typed lookup. The
discovery implementation in issue #203 consumes root-folder reads and artist creation for its
sealed handoff. The quality preset work in issue #213 consumes the already-generated custom-format,
quality-profile, and naming operations. All generated modules remain behind the stable
`LidarrClientApi` facade.
Generated operation names and wire types are maintainer implementation details, not package or
operator APIs.

The selected generator is the exact development dependency `@hey-api/openapi-ts@0.93.0`. Its
`@hey-api/client-fetch` plugin is configured with `bundle: true`, so the emitted Fetch runtime is
committed source and there is no separate runtime package dependency. TypeScript models and the full
flat SDK are generated with explicit per-instance clients, generated authentication disabled, and
NodeNext `.js` imports.

The only approved fallback is exact `openapi-typescript@7.13.0` with exact
`openapi-fetch@0.17.0`. Reconsider it only if the selected generator can no longer provide
per-instance custom Fetch, NodeNext imports, deterministic local generation, or compatibility with
the bounded reconstructed response.

## TsArr Evaluation

`tsarr@2.12.0` was evaluated in a temporary directory and was not added to the package or lockfile.
It declares Node `>=24.16.0`, while rfmedia supports Node `>=22.23.4`. A Node `v22.23.1` probe did
successfully import and construct the client and complete a mocked request, but an accidental smoke
success is not a supported runtime contract.

The probe also found three incompatible behaviors:

- Results exposed `{ data, request, response }` envelopes.
- Requests defaulted to redirect mode `follow`.
- Creating a second client replaced module-global configuration: calls through the first client
  used the second client's origin and API key.

That shared state fails the required two-client isolation, and TsArr does not supply rfmedia's
bounded parsing, strict domain projections, or error taxonomy. TsArr remains design evidence only.

## Generator Compatibility Normalization

The raw bundled client generated by `@hey-api/openapi-ts@0.93.0` contains exactly two `BodyInit`
type casts. rfmedia intentionally compiles with `lib: ["ES2023"]` rather than DOM globals, so the raw
tree fails strict compilation at those two references.

Generation applies one deterministic, type-only normalization:

```text
BodyInit | null | undefined -> RequestInit['body']
```

The generator wrapper requires exactly two raw matches, requires zero `BodyInit` references after
replacement, verifies the normalized file hash from the manifest, and compiles the entire staged
tree. Zero, one, or more than two matches fails closed. Maintainers must not add DOM libraries,
weaken TypeScript settings, or edit the emitted file to work around a mismatch.

## Architecture and Ownership

```text
commands
  -> actions
    -> stable LidarrClientApi facade and strict domain projections
      -> private named generated operations
        -> one hardened, per-instance Fetch transport
          -> Lidarr
```

| Owner                              | Responsibilities                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Generated SDK                      | Endpoint paths, HTTP verbs, query serialization, wire DTOs, and generated result envelopes                         |
| `client.ts` and `types.ts`         | Stable facade, operation selection, unknown-to-domain validation, fresh projections, and envelope non-escape       |
| `transport.ts`                     | Exact origin, off-object key access, header-only authentication, redirects, aborts, timeout, byte caps, and errors |
| Generator and architecture scripts | Manifest/config verification, atomic replacement, drift detection, and generated/manual import ownership           |

Generated modules are private, committed, and replace-only. Every emitted TypeScript file carries a
stable, timestamp-free machine-owned generator header. Never patch the generated tree manually;
change the immutable input, manifest, fixed configuration, or wrapper and regenerate the complete
tree.

## Artist Management Contract

The generator wrapper fails closed unless the snapshot and emitted SDK contain all operations needed
by the stable facade. Artist profile and tag management require:

- `GET /api/v1/artist` and `GET /api/v1/artist/{id}` for bounded list and targeted reads;
- `GET /api/v1/qualityprofile`, `GET /api/v1/metadataprofile`, and `GET /api/v1/tag` for exact
  resource resolution; and
- `PUT /api/v1/artist/editor` for the only supported artist mutation path.

The package does not re-export those generated operations. Actions depend on the narrow
`LidarrClientApi` methods `listArtists`, `getArtist`, `listQualityProfiles`,
`listMetadataProfiles`, `listTags`, `setArtistProfiles`, and `updateArtistTags`. The facade validates
unknown wire values into immutable domain projections and prevents generated envelopes, response
bodies, and writable wire models from escaping into actions.

The facade also owns every artist-editor request body. A profile request contains one `artistIds`
entry and only the requested `qualityProfileId` and/or `metadataProfileId`. A tag request contains
one `artistIds` entry, the exact tag IDs, and the `applyTags` mode derived from add, remove, set, or
clear intent. Unrelated writable artist fields are never copied from a read response.

An editor response means only that Lidarr accepted the request. The facade accepts any successful
2xx status, including `202`, and deliberately ignores the editor body. Plan apply establishes the
result with fresh `GET /api/v1/artist/{id}` reads: one immediately before dispatch and up to three
targeted reads after dispatch. If those bounded reads cannot prove the reviewed managed state, apply
records an uncertain outcome and stops instead of treating the editor body as verification or
blindly retrying the mutation.

## Quality Preset Contract

Quality preset packs consume committed generated operations that were already present in the pinned
OpenAPI snapshot:

| Facade methods                                                                            | Generated operations                                                                   | Required endpoints                                                                                   |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `listCustomFormats`, `getCustomFormat`, `getCustomFormatSchema`                           | `getApiV1Customformat`, `getApiV1CustomformatById`, `getApiV1CustomformatSchema`       | `GET /api/v1/customformat`, `GET /api/v1/customformat/{id}`, `GET /api/v1/customformat/schema`       |
| `createCustomFormat`, `updateCustomFormat`                                                | `postApiV1Customformat`, `putApiV1CustomformatById`                                    | `POST /api/v1/customformat`, `PUT /api/v1/customformat/{id}`                                         |
| `listQualityProfileDefinitions`, `getQualityProfileDefinition`, `getQualityProfileSchema` | `getApiV1Qualityprofile`, `getApiV1QualityprofileById`, `getApiV1QualityprofileSchema` | `GET /api/v1/qualityprofile`, `GET /api/v1/qualityprofile/{id}`, `GET /api/v1/qualityprofile/schema` |
| `createQualityProfile`, `updateQualityProfile`                                            | `postApiV1Qualityprofile`, `putApiV1QualityprofileById`                                | `POST /api/v1/qualityprofile`, `PUT /api/v1/qualityprofile/{id}`                                     |
| `getNamingConfig`, `getNamingExamples`, `updateNamingConfig`                              | `getApiV1ConfigNaming`, `getApiV1ConfigNamingExamples`, `putApiV1ConfigNamingById`     | `GET /api/v1/config/naming`, `GET /api/v1/config/naming/examples`, `PUT /api/v1/config/naming/{id}`  |

The facade boundary is intentionally richer than a thin generated-client wrapper. It validates
unknown response bodies into immutable preset-specific domain projections, validates positive IDs,
maps targeted `404` responses to `LidarrNotFoundError`, builds narrow create/update bodies, and
reconstructs nested quality items from the reviewed policy plus the live schema. Actions never
import generated operations or writable generated models, inspect generated result envelopes, or
copy an arbitrary live response back into a mutation.

Custom-format, quality-profile, and naming reads are explicitly classified as safe for in-place
retry by the resilience decorator. The corresponding `POST` and `PUT` facade methods are
deliberately absent from that allowlist. Preset apply dispatches those writes as non-idempotent tasks
in the `destructive` scheduler lane with zero facade retries, so neither layer automatically repeats
a write whose dispatch result is uncertain.

Issue #213 did not refresh `openapi/lidarr-v1.json` or its manifest. It only began consuming
operations already committed in the generated SDK and extended the offline generator assertions so
future regeneration fails closed if the required operations, request envelopes, or endpoints
disappear. The immutable provenance values above therefore remain unchanged.

See [Lidarr Quality Presets](lidarr-quality-presets.md) for pack discovery, semantic diff, approval,
ordered application, and recovery behavior.

## Search and Lookup Contract

The generator wrapper also fails closed unless the snapshot and emitted SDK contain the three
read-only search operations:

| Facade method   | Generated operation    | Required endpoint           |
| --------------- | ---------------------- | --------------------------- |
| `search`        | `getApiV1Search`       | `GET /api/v1/search`        |
| `lookupArtists` | `getApiV1ArtistLookup` | `GET /api/v1/artist/lookup` |
| `lookupAlbums`  | `getApiV1AlbumLookup`  | `GET /api/v1/album/lookup`  |

Each method accepts a validated term and optional caller `AbortSignal`. The facade passes the term
as the generated `term` query parameter and the signal as request context. Actions never import a
generated operation, construct an `/api/v1/` path, configure authentication, or inspect the
generated `{ data, request, response }` envelope.

The response boundary is strict and atomic:

- `search` accepts a bounded array whose entries contain exactly one artist or album payload;
- `lookupArtists` accepts artist candidates only;
- `lookupAlbums` accepts album candidates only;
- every durable artist or release-group identity is a valid MusicBrainz UUID;
- the array contains at most 1,000 entries and projected display strings are bounded and
  control-free; and
- any malformed or ambiguous entry rejects the whole response as `invalid-response`.

The generated-independent candidate projection contains only `kind`, `foreignId`, `name`, optional
positive `lidarrId`, and the bounded type-specific display fields. A combined response's outer `id`
is not treated as durable identity. Profiles, monitoring state, paths, tags, images, links, tracks,
releases, writable models, raw response fields, and generated types do not escape the facade.

## Discovery Artist-Add Contract

Issue #203 does not generate or expose a Last.fm SDK. Its fixed provider transport is a separate
handwritten boundary. Only an MBID-backed selected recommendation can reach the Lidarr facade, and
only after it has been sealed into an expected-absence `artist-add` plan.

The generator wrapper fails closed unless the committed Lidarr snapshot and emitted SDK contain:

| Facade method                                        | Generated operation       | Required endpoint             |
| ---------------------------------------------------- | ------------------------- | ----------------------------- |
| `listRootFolders`                                    | `getApiV1Rootfolder`      | `GET /api/v1/rootfolder`      |
| `listMetadataProfiles`, `listMetadataProfileDetails` | `getApiV1Metadataprofile` | `GET /api/v1/metadataprofile` |
| `listAlbums`                                         | `getApiV1Album`           | `GET /api/v1/album`           |
| `setAlbumsMonitored`                                 | `putApiV1AlbumMonitor`    | `PUT /api/v1/album/monitor`   |
| `addArtist`                                          | `postApiV1Artist`         | `POST /api/v1/artist`         |

The existing artist lookup and complete artist-list methods provide exact-MBID identity and
expected-absence checks. Generated source was not edited and the immutable OpenAPI provenance did
not change; artist add consumes only already-committed operations pinned by offline generator and
contract checks.

The compatible `listMetadataProfiles` method remains the narrow frozen `{id, name}` projection used
by existing profile resolution. Artist-add planning uses the separate strict
`listMetadataProfileDetails` boundary. It validates a bounded response atomically and returns
positive profile IDs, bounded names, and complete frozen primary and secondary album-type arrays.
Every album-type record contains a positive type ID, bounded name, and boolean `allowed` value;
duplicate record IDs or type IDs reject the response. Generated metadata-profile DTOs remain
private.

When `--metadata-profile` is omitted, planning uses that structural evidence rather than a profile
name. An albums-only profile must allow exactly the primary type named `Album` and no secondary
type. The selected root folder's default wins only when it meets that rule; otherwise exactly one
structurally eligible profile must exist.

`client.ts` alone constructs the writable artist body from one authoritative exact Lidarr lookup
and the sealed root-folder, quality-profile, and metadata-profile references. It maps the reviewed
artist `monitored` boolean into the live request while fixing `monitorNewItems: "none"`,
`addOptions.monitor: "none"`, and `addOptions.searchForMissingAlbums: false`. Provider wire records,
arbitrary live artist fields, API keys, and generated writable models never escape the facade.

`addArtist` is non-idempotent, absent from the resilience retry allowlist, and invoked only by the
registered non-deferable plan/apply operation. Apply writes possible-dispatch evidence before the
request and reconciles with a fresh exact-MBID read rather than retrying a possibly completed
create.

Optional post-add normalization also stays behind the facade. Apply reads only
`listAlbums({artistId})`, filters the reviewed canonical album-type selectors locally, and sends
sorted matching album IDs to `setAlbumsMonitored(..., false)` in batches of at most 200. A fresh
artist-scoped album read must prove no selected type remains monitored; an empty read is
inconclusive. Normalization never calls `addArtist` a second time. See
[Lidarr Similar-Artist Discovery](lidarr-discovery.md) and
[Lidarr Mutation Plan/Apply](lidarr-plan-apply.md).

The search operations were already present in the pinned snapshot, so issue #222 requires no
network refresh, provenance change, generated file-count change, runtime dependency, or
third-party-notice change. Offline generation and drift checks nevertheless require the exact
operations and endpoints so future snapshot changes cannot silently remove the supported contract.

See [Lidarr Search and Lookup](lidarr-search-lookup.md) for the operator-facing commands, candidate
model, paging, and cache behavior.

## Maintainer Commands

Run these commands from the repository root.

### Offline regeneration

```bash
npm run codegen:lidarr --workspace packages/rfmedia-cli
```

This validates the local manifest, snapshot, exact dependency and config identities, generates and
compiles in a confined temporary directory, and atomically replaces the complete generated tree.

### Offline non-mutating drift check

```bash
npm run codegen:lidarr:check --workspace packages/rfmedia-cli
```

Check mode compares sorted relative paths, entry types, and bytes. It reports changed, missing,
extra, type-mismatched, symlink, and non-file entries without repairing or otherwise modifying the
working tree. Its repair command is the offline regeneration command above.

### Offline tooling tests

```bash
npm run test:codegen:lidarr --workspace packages/rfmedia-cli
```

The generator tests use temporary fixtures. Refresh tests use mocked Fetch and never contact
GitHub, Lidarr, or another live service.

### Explicit network refresh

```bash
npm run openapi:lidarr:refresh --workspace packages/rfmedia-cli -- <40-hex-commit>
```

This is the only workflow permitted to contact the upstream GitHub endpoints. It accepts exactly one
full immutable commit, constructs only the allowlisted `Lidarr/Lidarr` raw and Contents URLs for the
fixed path, rejects redirects, and caps time and response bytes. Before installation it validates
UTF-8 JSON, OpenAPI 3.0.4, local-only references, every required endpoint contract, both API key
schemes, exact-byte SHA-256, and the Git blob SHA returned by GitHub. It then stages the snapshot,
manifest, and complete generated output and installs them together with last-known-good rollback.

No schema field, environment variable, or CLI argument can select a host, repository, path, output,
plugin, package, or command. Ordinary `npm ci`, build, typecheck, tests, runtime use, and CI do not
fetch from GitHub or Lidarr. An install may contact the configured npm registry for dependencies, but
it never refreshes the Lidarr schema.

## Refresh and Upgrade Review

After a refresh, leave every change uncommitted until a human reviews these trust classes separately:

1. Snapshot and manifest: confirm immutable repository/path/commit, Git blob SHA, exact-byte SHA-256,
   OpenAPI version, required operations, security schemes, and license metadata.
2. Generator config and lockfile: confirm exact versions, integrity, bundled-client mode, no lifecycle
   hook, and no new production dependency.
3. Generated tree: review endpoint, wire-model, auth, parsing, and runtime changes as replace-only
   output; run the non-mutating drift check.
4. Handwritten facade and transport: verify the generated/manual ownership boundary and both critical
   security controls below.
5. Tests and documentation: review generated contract names, runtime projections, fixtures, notice,
   and parity between the implemented operator surface, documentation, and all shell completions.
6. Package surface: repeat the size, timing, and `npm pack --dry-run --json` inspection. Search the
   complete diff and proposed tarball list for secrets.

A generator upgrade follows the same procedure and additionally updates every exact generator,
tarball, integrity, raw-runtime hash, normalized-runtime hash, and normalization assertion in the
manifest. Repeat the Node 22 import/request probe, two-client concurrency test, transport adversarial
tests, strict projections, deterministic reruns, full package validation, and pack inspection.

## Failure Recovery and Rollback

- If drift check reports changed, missing, extra, symlink, non-file, or type differences, inspect the
  unexpected entry and run the documented offline regeneration command. Do not delete or hand-repair
  individual generated files.
- If generation, normalization, compile, or refresh validation fails, fix the authoritative input or
  wrapper. Atomic staging preserves the last-known-good generated tree; refresh also preserves the
  last-known-good snapshot and manifest.
- If a reviewed change must be rolled back, revert the repository commit containing the snapshot,
  manifest, config, generated tree, transport/facade, tests, and notice together, then rerun offline
  drift and package validation. Do not mix versions across those files.

## Security Invariants

`SEC-194-01` and `SEC-194-02` are merge stops, not best-effort checks.

### SEC-194-01: request and credential confinement

- Each `LidarrClient` owns one private generated client and one hardened Fetch closure.
- The transport validates the final generated Request before retrieving the origin-bound API key.
- Only the exact canonical HTTP(S) origin is allowed; credentials, fragments, credential-like query
  keys/values, and pre-existing authentication headers are rejected.
- The transport injects exactly one `X-Api-Key` header, never query authentication, and forces
  `redirect: "error"` immediately before trusted Fetch.
- Concurrent clients and operation contexts must not exchange origins, keys, or error labels.

### SEC-194-02: bounded parsing

- The timeout and caller cancellation remain active through the complete response-body read.
- Decoded response streams are counted as read: success is capped at 8 MiB and error drain at 4 KiB,
  independent of missing, invalid, understated, or misleading `Content-Length`.
- Readers are cancelled on overflow or abort. Success bytes must pass fatal UTF-8 decoding.
- Generated code receives only a bounded reconstructed response. Raw requests, responses, headers,
  bodies, parser errors, and generated envelopes never cross the stable facade or enter error causes.

## Package and Performance Baseline

Measured locally on Linux `6.8.0-136-generic` x86-64 with Node `v22.23.1` and npm `11.17.0`.
Durations are local baselines, not CI performance requirements.

| Measurement                     | Result                                                                                                   |
| ------------------------------- | -------------------------------------------------------------------------------------------------------- |
| OpenAPI snapshot                | 316,102 bytes                                                                                            |
| Generated source                | 16 files, 295,016 bytes                                                                                  |
| Tracked codegen maintenance set | 23 files, 682,709 bytes                                                                                  |
| Package typecheck               | 11.11 s elapsed; 23.00 s user; 2.21 s system; 545,484 KiB maximum RSS                                    |
| Cold-process `rfmedia --help`   | 10 new Node processes with warm filesystem/cache: 163.66 ms minimum, 176.49 ms median, 200.66 ms maximum |
| `npm pack --dry-run --json`     | See the reviewed package-content result below                                                            |

The tracked maintenance set is defined as the snapshot, manifest, generator config, 16 generated
source files, and both generation/refresh scripts with their tests. Typecheck used the exact package
command under Node 22. The help baseline invoked the built `dist/bootstrap.js --help` in ten separate
Node 22 processes, captured output, and required the usage marker; it is process-cold but uses warm OS
filesystem caches.

The final dry-run used:

```bash
npm pack --dry-run --json --workspace packages/rfmedia-cli
```

The final post-documentation result was 1,502 entries, a 2,553,434-byte tarball, and 14,340,744
unpacked bytes. The package has no `files` allowlist or `.npmignore`; npm therefore used `.gitignore`
fallback. Review confirmed inclusion of the OpenAPI snapshot/manifest, third-party notice, this
feature guide, generated TypeScript source, compiled generated JavaScript/declarations/maps, tests,
and planning documentation. This is broader than a minimal runtime package. A suspicious-filename
audit found no `.env`, private-key, or credential file, and a focused content scan found no common
private-key, AWS access-key, GitHub token, or OpenAI key signature. Source fixtures and security tests
do contain intentional placeholder words such as `secret` and `token`. Maintainers must repeat the
audit rather than treating the current result as permanent.
