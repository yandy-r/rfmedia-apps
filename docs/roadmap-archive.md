### Operator notes from shipped lifecycle work

- **Managed updates (#148 / #239):** operator-invoked and sequential; recovery restores the prior
  image on the same Docker daemon under current Compose config — not volumes, app data, DBs, or
  migrations. Unattended scheduling remains open in [#169](https://github.com/yandy-r/rfmedia-apps/issues/169).
- **Reconcile (#151 / #244):** report-first; `--auto-apply` is explicit authorization. See
  [reconciliation guide](features/rfapps-reconcile-command.md).
- **State locking (#65 / #265):** CLI and MCP mutations share a private lock in the selected XDG or
  legacy state directory; read-only and dry-run paths remain lock-free. Stale locks fail closed and
  require an operator-verified `rfapps force-unlock`.
- **Service conflict detection (#64 / #271):** opt-in `deploy --validate-first` resolves the
  effective service closure and reports deterministic Docker-owned port, volume, and network
  conflicts before mutation. Required evidence and pre-mutation binding changes fail closed.
- **Runtime state import (#149 / #267):** `rfapps import` adopts an existing Compose/runtime stack
  into managed state without recreating containers.
- **State rebuild (#150 / #269):** `rfapps state rebuild` (plus export) recovers managed state when
  the state DB and live Docker diverge.
- **Staged deployment (#159 / #273):** opt-in `deploy --staged` rolls a group out in
  dependency-ordered batches, canary first and `core`-profile services last, and gates each batch on
  the health of the services it just started. A failing batch halts by default; later services are
  never touched and are recorded as `STAGE_NOT_ATTEMPTED` so a halt exits `1` (or `3` with
  `--allow-partial`). Healthcheck-less services get `running-only` assurance from a bounded soak,
  and completed one-shot containers are exempt. The rollout holds the state lock for its whole
  duration, so rfapps warns when the worst case outruns the 10-minute staleness threshold. Closes
  the rfapps state & deploy hardening track. See
  [staged rollout docs](../packages/rfapps-cli/README.md#staged-rollout).
- **Contextual plan intelligence (#152 / #296):** opt-in `rfapps plan --explain` adds bounded,
  deterministic cause, impact, and dependency evidence without changing the default plan contract
  or apply authorization.
- **Native backup (#160 / #297):** `rfapps backup` creates manifest-last cold filesystem backups
  with daemon-authoritative bind/destination checks, full writer quiescing, exact container
  recovery, and explicit retained-incomplete evidence. `rfapps backup verify` validates size and
  SHA-256 evidence offline without Docker, config, or a state lock. Bash, Zsh, and Fish completions
  ship in parity. See [native backup docs](features/rfapps-backup.md).
- **Image vulnerability scanning (#161 / #300):** opt-in `--scan` on `rfapps plan` and
  `rfapps deploy` scans the image references `docker compose config` resolves, one scanner process
  per distinct image, with `trivy` or `grype` selected explicitly — a requested-but-absent scanner is
  reported by name, never silently substituted. Scanning is advisory by default
  (`--scan-fail-on none`); once a threshold is set the gate is fail-closed, so a missing scanner, a
  per-image timeout, a capture overflow, or an unparsable report all resolve to `inconclusive` and
  block rather than passing on zero findings. Deploy's gate runs before pull and before any
  container mutation, and `deploy --dry-run --scan` still reports a would-block gate while
  exiting 0. The report rides the plan/deploy output envelope and is never persisted into the saved
  plan artifact, so `rfapps apply <path>` cannot re-assert a stale CVE verdict days later. Operator
  notes: images are scanned as compose resolves them, so a mutable tag describes whatever the
  registry serves at scan time — pin digests in `compose.yml` for a hard guarantee; there is no
  finding cache and no SBOM/SARIF export; `scan.ignore` suppressions require a reason and expire
  through `until`; and scan arguments are deliberately absent from the MCP surface. See
  [vulnerability scanning docs](features/rfapps-vulnerability-scanning.md).
- **Security hardening automation (#162 / #300):** `rfapps harden` proposes compose security
  changes across capabilities, identity, filesystem mode, logging, resource limits, health checks,
  and restart availability. Detection reads the resolved compose config, every write goes through
  the comment- and anchor-preserving YAML document, and the rule catalog is namespaced `harden-*`
  so shipped `rfapps lint` and `rfapps audit` output is unchanged. Propose mode is the default and
  writes nothing; `--out` emits an override fragment without clobbering an existing file; `--apply`
  edits `compose.yml` in place only after a `.bak` copy and a confirmation. Only `safe` proposals
  are written (`--include-review` adds the `review` tier), and the three advisory rules — health
  check, memory limit, cpu limit — are detection plus guidance by design: rfapps will not invent a
  probe command or a resource ceiling. A patch aimed at a YAML alias is refused with the `--out`
  alternative rather than rewriting every service that shares the anchor; override fragments emit
  the full resulting list for sequence-valued keys, because a compose override replaces sequences
  instead of appending to them; and `--apply` refuses to reformat lines it did not target unless
  `--allow-reformat` is given. Harden is not a findings gate and has no `--fail-on`: refusals are
  reported, and exit 3 means `--apply` wrote some patches and withheld others. Bash, Zsh, and Fish
  completions ship in parity. See [harden docs](features/rfapps-harden-command.md).
- **Tiered verify (#116 / #249):** quick / default (schema-v9 SHA-256) / deep; historical ranged
  outputs without represented fingerprints report `unverifiable`.
- **Plex adapter (#119 / #252):** provider-neutral `MediaServerAdapter`; JWT enrollment shipped
  separately in #251 (below).
- **Plex JWT enrollment (#251 / #291):** `rfmedia plex auth login|status|refresh|logout` enrolls a
  device credential and rotates it ahead of expiry from a durable, operator-owned store. Operator
  notes: revocation is **local-only** — `logout` destroys local key material, the device stays
  authorized on the account until it is removed by hand at
  [app.plex.tv](https://app.plex.tv/desktop/#!/settings/devices/all), which is why every result
  reports `serverSideRevocation: "manual"` (a client-callable endpoint is tracked in
  [#286](https://github.com/yandy-r/rfmedia-apps/issues/286)). The store must live on a **local
  filesystem** — atomic replace, private modes, and the advisory lock are not guaranteed over
  NFS/SMB — and is relocatable with `RFMEDIA_PLEX_AUTH_DIR`. `login` requires a reachable Plex Media
  Server and discards the freshly minted credential when the probe rejects it, so each retry mints a
  new PIN against an IP-scoped budget. Enrollment was **not** exercised end-to-end against a real
  account: the token-endpoint success body (U1) and PMS acceptance of a plex.tv-issued JWT (U6)
  remain unobserved; both are contained in the tolerant wire reader and the discard-on-reject probe.
  Deferrals, residual risk, and accepted debt are recorded in
  [`docs/internal/plex-jwt-deferrals.md`](internal/plex-jwt-deferrals.md).
- **Radio-scheduling separation (#113 / #264):** playlist sequencing rules documented and covered by
  tests; completes rfmedia `priority:high` work.
- **Metadata reconciliation (#125 / #295):** `rfmedia reconcile scan|apply` compares normalized
  file tags, rfmedia SQLite rows, and fresh media-server snapshots. Scan is report-only; apply
  requires exactly one explicit `file-wins`, `db-wins`, or `server-wins` strategy. Changed evidence,
  stale database generations (including uncheckpointed WAL commits), unsupported mutation targets,
  and failed postconditions remain residual instead of being overwritten. Linux MP3 rating writes
  use trusted descriptor-anchored atomic publication; FLAC and other local formats remain observable
  but unsupported for reconciliation mutation. Bash, Zsh, and Fish completions ship in parity. See
  [metadata reconciliation docs](../packages/rfmedia-cli/docs/features/metadata-reconciliation.md).
- **Lidarr foundation (#193 / #197 / #194):** `rfmedia lidarr` namespace, generated OpenAPI client,
  and baseline read-only commands.
- **Lidarr resilience and mutation safety (#195 / #196 / #202):** persisted circuit/deferred state,
  tiered execution lanes, and a sealed plan/apply boundary with exact-ID artist monitoring.
- **Lidarr Layer 1 suite (#198–#200, #211, #213, #216, #222–#223):** bulk unmonitor / album-type controls,
  mass profile & tag management, search/lookup, album management, file-aware artist deletion, and
  deterministic quality/custom-format/naming preset management with plan/apply guardrails. The
  closing piece is `lidarr audit` (#211): a strictly read-only diagnostic that runs 7 active checks
  plus 1 reserved `plex-alignment` slot, now directing operators to `rfmedia lidarr reconcile`,
  reports every check with a machine-readable status, and stays diagnostic by default — exit codes
  are only gated when an operator opts in with `--fail-on`. The final #216 surface adds read-only
  manual-import matching plus fail-closed, exact-album trackfile filtering through sealed
  plan/apply. Bulk
  import/export remains optional in #201.
- **Last.fm discovery and safety (#203 / #277, #205 / #278, #206 / #279):**
  `rfmedia lidarr discover` performs
  attributed, uncached similar-artist discovery without resolving Lidarr by default. Discovery is
  preview-first, one hop by default, and bounded by similarity, exposure, diversity, quarantine,
  fan-out, loop-prevention, and fixed-depth controls. Explicit comma-separated rank approval can
  create one sealed, ordered multi-entry `artist-add` plan; mutation remains confined to
  `lidarr apply`, where exact-MBID expected absence, possible-dispatch evidence, and reconciliation
  prevent blind retries. Artist-add plans now default to unmonitored, no-search behavior and a
  structurally verified albums-only metadata profile; explicit overrides are sealed into the plan,
  and durable post-add normalization stages resume without repeating artist creation. Federated
  providers (#204) remain optional.
- **Cascade analysis and indexer budgets (#219 / #280):** every live Lidarr plan producer now seals
  deterministic immediate and conditional impact evidence into strict v3 artifacts. Configured
  per-plan acquisition/indexer allowances produce advisory warnings and recommendations without
  changing apply authorization, scope, or scheduling. Exact v1/v2 checksum, read, validation, and
  apply compatibility remains intact.
- **Plex–Lidarr artist identity (#207 / #283):** provider-neutral Plex acquisition projects bounded
  artist MBIDs, unique exact MBIDs are the sole automatic-match authority, name scoring remains
  advisory, and complete provider-instance snapshots persist through a strict fail-closed SQLite
  cache.
- **Plex–Lidarr reconciliation (#208 / #284 / #285):** `rfmedia lidarr reconcile` produces a
  deterministic report of exact-only authoritative matches, review-only name evidence, and
  directional Plex/Lidarr gaps. Snapshot v2 retains the bounded minimal Lidarr catalog required for
  truthful offline reverse gaps; `--offline` selects exactly one compatible cached scope and exposes
  its age and provenance. A complete live run may atomically replace the observational cache, but
  live and offline modes never mutate Plex or Lidarr, generate policy, or authorize remediation.
  Ratings-driven decisions (#221) now ship on top of it as `rfmedia lidarr sync-ratings`.
- **Consumption-driven policy engine (#209 / #292):** `rfmedia lidarr policy evaluate` joins Plex
  play and rating signals onto the reconciled identity bridge and reports explainable proposed Lidarr
  actions. Strictly read-only: no Plex write, no Lidarr mutation, and no plan artifact. Three rules
  ship — `rating-quality-upgrade`, `stale-monitoring-cleanup`, `discovery-seed` — all disabled by
  default, and only a unique exact artist-MBID join may carry a proposal (enforced by a branded type,
  not review discipline). Every proposal and refusal carries a stable decision key, the threshold
  arithmetic behind it, and the dotted `.rfmedia.yaml` key of each configured bound; `--explain <key>`
  prints the full causal chain under human output. Operator notes: play counts and `lastViewedAt`
  belong to the single Plex account behind the resolved credential. Recency is opt-in through
  `minDaysSinceLastViewed`, remains conjunctive with the absolute `maxPlays` ceiling, and refuses
  missing or partial timestamp coverage. Consumption still rolls up to the **album** artist through
  a weak normalized-name join, so compilation-only listening may not reach the performer's own
  bucket. `--rule` narrows which rules evaluate but not the full-library Plex track drain —
  `plex.cache.enabled: true` is the only lever on that cost. Reaching a mutation still takes three
  separate operator-typed commands (`policy evaluate` → `lidarr plan …` →
  `lidarr apply --plan-file … --yes`). `skipCount` and id-joined play counts remain deferred. The
  dispute/override surface shipped in #313 / PR #317. See
  [consumption policy docs](../packages/rfmedia-cli/docs/features/lidarr-consumption-policy.md).
- **Plex ratings sync to Lidarr decisions (#221 / #294):** `rfmedia lidarr sync-ratings`
  is the gated apply lane for the two policy rules that own a plan producer —
  `rating-quality-upgrade` → `artist-profile-assignment` and `stale-monitoring-cleanup` →
  `artist-monitoring`. It decides nothing of its own: it runs the shipped policy engine, projects its
  proposals onto the shipped producers, and embeds the evaluation report verbatim, so it and
  `policy evaluate` are structurally incapable of disagreeing about a decision. A single
  value-taking `--mode <recommend|plan|apply>` is the entire write envelope — `recommend` (the
  default) calls no producer, `plan` seals 0-2 mode-`0600` artifacts and applies nothing, and `apply`
  additionally requires `--yes` under machine output or a non-interactive stdout. `discovery-seed` is
  structurally absent because it owns no producer, and **nothing is ever written back to Plex** under
  any flag combination. Operator notes: play totals are a **weak normalized-name rollup** — Plex
  tracks carry the album artist as a bare string with no id, so the join is by normalized name and
  fails closed three ways (`sentinel-artist-name`, `ambiguous-name-join`, `no-consumption-coverage`),
  a compilation-only performer reads as zero plays under their own name, and a library-wide zero
  (`consumption-signal-empty`) almost always means the resolved token is not the listening account.
  `--max-plays` remains an absolute lifetime ceiling; config-only `minDaysSinceLastViewed` adds an
  optional recency conjunction without replacing it. Missing or partial timestamps refuse the
  affected artist, and neither `skipCount` nor per-item `addedAt` is inferred. `--quality-profile`
  resolves numeric ids **before** names, which is why the report echoes the resolved id and name as
  a pair, and an artist proposed by both decisions is withheld from both with
  `cross-decision-conflict` rather than sealed into two independently applied artifacts. See
  [ratings sync docs](../packages/rfmedia-cli/docs/features/lidarr-ratings-sync.md).
- **Policy decision overrides (#313 / #317):** bounded `policy.overrides` entries suppress one
  stable decision key only while its SHA-256 evidence fingerprint still matches. Evaluate, plan,
  and ratings sync share the same reconciliation; stale and not-evaluated entries remain visible,
  and overrides alone never mutate Lidarr or bypass sealed-plan authorization. Authoritative config
  reads bypass cache and fail closed on malformed, unreadable, or dangling paths. See the
  [dispute workflow](../packages/rfmedia-cli/docs/features/lidarr-consumption-policy.md#disputing-a-decision).
- **Plex recency policy signals (#314 / #318):** typed `lastViewedAt` epoch seconds flow through the
  private Plex adapter into per-artist consumption evidence. The opt-in whole-day threshold uses a
  captured evaluation time, inclusive 86,400-second days, raw timestamp fingerprints, and stable
  ISO explain checks. Missing, partial, count-inconsistent, or non-ISO-renderable timestamps fail
  closed; no history is persisted, no command or apply surface changes, and `skipCount` remains
  deferred until Plex exposes a trustworthy contract.
- **Secure-store completion (#288 / #304–#308 / #307):** claim locks and plan document I/O sit on
  `secure-store` (PRs #309, #319, #331). The lock error taxonomy was corrected in PR #333 (#308).
  Staging now `fchmod`s the stage handle so `verify --fix` no longer publishes a read-only file under
  a restrictive umask (#307 / PR #336). Follow-ups filed from that fix: [#334](https://github.com/yandy-r/rfmedia-apps/issues/334)
  (repaired file publishes `0600` rather than a destination-derived mode) and
  [#335](https://github.com/yandy-r/rfmedia-apps/issues/335) (same umask-masking defect in rfapps
  `backup-docker`). [#323](https://github.com/yandy-r/rfmedia-apps/issues/323) remains a separate

- **Hierarchical service tagging (#63 / #332):** `--tag <pattern>` is a narrowing selector axis on
  21 command paths, plus the read-only `rfapps tag list | show | suggest` inspection group. Tags live

  (exit 2) rather than collapsing into the whole-project `services: []` sentinel. Deliberately
  read-only in v1 and not MCP-surfaced. See
  [`docs/features/rfapps-tag-selector.md`](features/rfapps-tag-selector.md).
