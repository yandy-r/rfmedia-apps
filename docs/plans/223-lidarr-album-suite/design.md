# Issue #223 — Lidarr Album Management Suite: Final Design

All paths relative to `packages/rfmedia-cli/` unless noted. Ground truth: current worktree code (spot-checked); PRs #259/#260/#261 are shipped.

## 1. Overview

Issue #223 asks for album list/filter, monitor/unmonitor, targeted edits, and safe deletion. Monitor/unmonitor **shipped** in PR #259. This design delivers the true remaining scope:

1. **`rfmedia lidarr albums`** — read-only album list/filter leaf (artist-, ID-, or explicitly-authorized library-scoped), with reliable client-side pagination over a deterministic sort.
2. **`rfmedia lidarr plan album-delete`** + apply authorization — the first file-destructive Lidarr operation, hosted in the v2 sealed-plan lane via a **parallel album-typed operation definition** (no genericization of the artist machinery), with missing-target==satisfied idempotency and bounded post-dispatch absence verification.
3. **`rfmedia lidarr plan album-edit`** — targeted `anyReleaseOk` (release-policy) edits, the only remaining SDK-editable album scalar beyond monitored; rides the same album-typed v2 machinery; severable final phase.
4. **Reusable album selection primitives** — pure `lib/lidarr/album-selection.ts` + shared I/O `actions/lidarr/album-scan.ts`, extracted behavior-identically from `plan-albums.ts` (existing tests are the regression net).

## 3. Command surface

### 3.1 `rfmedia lidarr albums` (NEW read leaf, registered after `list`)

Description: "List Lidarr albums with type, monitored-state, and file filtering". New pinned order: `status, list, albums, wanted, health, search, lookup, plan, apply` (update src/commands/lidarr.test.ts:588-608).

- **Scope** (exactly ONE required; enforced via `MissingRequiredArgumentError` in `.action()` before the lazy action import, message "Choose exactly one selection scope: --artist-ids, --album-ids, or --all"; helpGroup "Selection:"):
  - `--artist-ids <ids>` — deps.parseIdList("Artist", …); conflicts albumIds, all
  - `--album-ids <ids>` — deps.parseIdList("Album", …); fail-closed on missing/extra IDs; conflicts artistIds, all, types
  - `--all` — explicit opt-in to a library-wide per-artist scan; conflicts artistIds, albumIds
- **Filters** (AND across dimensions): `--types <list>` (parseAlbumTypeSelectors, OR within selectors; conflicts albumIds); `--monitored`/`--unmonitored` (mutual conflicts); `--has-files`/`--no-files` (mutual conflicts; `statistics.trackFileCount ?? 0 > 0`; documented that absent statistics counts as 0 files).
- **Paging**: `--limit <n>` (parsePositiveInt, default 50), `--offset <n>` (parseNonNegativeInt, default 0), applied AFTER a fixed deterministic sort (artistId asc, then albumId asc) so windows are stable across invocations. No sort flags (rejected below).
- **Connection**: `--lidarr-url`, `--lidarr-api-key`. **NO `--allow-stale`** (no album metadata-cache category, src/lib/lidarr/metadata-cache.ts:19; `staleHint:false`). Failure id "albums" → envelope command `lidarr-albums`, `sensitiveValues:[lidarrApiKey]`.
- **Output**: human stderr table (Album ID, Album, Artist, Type, Monitored, Files as trackFileCount/trackCount, Size via formatBytes, Release) + scan/window summary line + renderExecutionSummary; machine stdout `{command:"lidarr-albums", result}`; CSV = stable **multi-row** exported `LIDARR_ALBUMS_CSV_COLUMNS` (search precedent, src/commands/lidarr-search.ts:59-92).

Examples:

```
rfmedia lidarr albums --artist-ids 12 --types singles,eps --unmonitored
rfmedia lidarr albums --all --unmonitored --no-files --limit 100 --offset 200 --output json
rfmedia lidarr albums --album-ids 55,102 --output csv
```

### 3.2 `rfmedia lidarr plan album-delete` (NEW plan leaf, registered LAST under `plan`)

New pinned plan order: `artist-monitoring, album-monitoring, artist-profiles, artist-tags, album-edit, album-delete` (ORDER-SENSITIVE comment at src/commands/lidarr.ts:969-971; destructive last).

- **Selection** (exactly one mode; NO `--all` — library-wide destructive sweeps are unexpressible):
  - `--album-ids <ids>` (explicit; fail-closed on missing/extra/orphaned), OR
  - `--artist-ids <ids>` **REQUIRED** in selector mode, optionally narrowed by `--types <list>`. `--types` without `--artist-ids` rejected: "album deletion requires an explicit --album-ids or --artist-ids scope".
- **Monitored guard**: monitored albums EXCLUDED by default (counted as `excludedMonitored` in the selection summary); `--include-monitored` opts in.
- **Destruction mode** (sealed into the checksummed artifact; not re-decidable at apply): `--delete-files` (default false = library-removal only), `--add-import-list-exclusion` (default false).
- **Safety/output**: `--dry-run` (conflicts planFile), `--max-batch <n>` (deps.parseMaxBatch, default 25, cap 1000), `--plan-file <path>` (deps.assertSafePlanFileArgument), connection flags. No `-v` (matches the album-monitoring leaf's locked asymmetry).
- **Human plan render**: red bold DESTRUCTIVE banner; mode line ("removes N albums from the library" / "PERMANENTLY DELETES M track files, X GB on disk"); risk cascade; sample table capped at 20 rows (Album ID, Album, Artist, Files, Size, Monitored); authorization hint naming the exact apply flags.

Examples:

```
rfmedia lidarr plan album-delete --artist-ids 12 --types demos,mixtapes --dry-run
rfmedia lidarr plan album-delete --album-ids 4501,4502 --delete-files --plan-file plans/del.json
```

### 3.3 `rfmedia lidarr plan album-edit` (NEW plan leaf, registered after `artist-tags`)

Description: "Plan album release-policy (any-release-ok) changes".

- **Selection**: same triad as album-monitoring (src/commands/lidarr-albums.ts:192-208): `--album-ids` (conflicts types, artistIds) | `--types <list>` [`--artist-ids <ids>`]; one of types/albumIds required.
- **Desired change** (one required, checked in `.action()`): `--any-release-ok` / `--no-any-release-ok` (Commander positive/negative pair → one boolean; error "Pass --any-release-ok or --no-any-release-ok"; monitoring changes error-hint to `plan album-monitoring`).
- **Safety/output**: `--dry-run` (conflicts planFile), `--max-batch`, `--plan-file` (sanitized), connection flags; no `-v` (album-leaf convention). Entries are changes-only (`before.anyReleaseOk !== desired`); fail-closed when Lidarr omits anyReleaseOk for a matched album.

Example: `rfmedia lidarr plan album-edit --artist-ids 42 --types albums --no-any-release-ok --plan-file edit.json`

### 3.4 `rfmedia lidarr apply <plan-file>` (MODIFIED — two Safety flags beside `--allow-tag-replacement`, src/commands/lidarr.ts:1123-1127)

- `--allow-album-deletion` — required for ANY real (non-dry-run) apply of an album-delete plan.
- `--allow-file-deletion` — ADDITIONALLY required when the sealed plan has `operation.deleteFiles === true` (two-key ceremony; name chosen for reuse by #200).

Both are **authorization** (plan-kind gates), distinct from **approval** (`--yes`) — required even with `--yes`, exactly like the tag gate. Enforced twice: command layer via new presenter helpers `requiresAlbumDeletionAuthorization`/`requiresFileDeletionAuthorization` (pattern lidarr.ts:1168-1172) and action layer in `executeLidarrApply` (beside apply.ts:686-696). Dry-run requires neither. Interactive confirm label: "destructive album-deletion (N albums, M files, X GB)"; recoveryCommand echoes authorization flags. album-edit applies need no authorization flag (non-destructive) but keep the standard review/confirm/--yes flow.

## 4. Architecture

**Lane decision (verified against code)**: new album operations join the **v2 artifact schema via a PARALLEL album-typed operation definition** — not v1 extension, not v2 genericization.

- v2 validators dispatch per `operation.kind` (`requireOperationV2` plan-engine.ts:1358-1412, `requireEntryV2` :1484+); `requireEntryIdentity` (:1470-1482) is only called from artist cases — new album cases are additive and never touch artist code.
- `buildLidarrMutationPlanV2` (:976-1034) hard-codes artistId sort/dedupe (:995-1004) → album plans use a **separate builder** in the new module, sealed with the shared checksum/createdBy helpers, version string stays `rfmedia.lidarr-plan.v2`.
- The v2 definition interface hard-codes `current: LidarrArtist` (plan-operation-definitions.ts:119-124) → album definitions implement a sibling album-typed interface; `apply.ts` already unions two definition shapes (:86-88), so a third member is precedented.
- The v1 lane stays frozen byte-for-byte (its interface hard-codes monitoring shapes end-to-end, plan-engine.ts:211-265); v1 fixtures untouched.

### Data flow (delete)

plan leaf → producer → album-scan (fail-closed) → filter + monitored-exclusion → `buildLidarrAlbumMutationPlanV2` (albumId-sorted, deduped, checksum-sealed, sealed selection context) → `writeLidarrPlanArtifact` (0600, atomic, no-overwrite) → operator review (plan render / apply --dry-run) → `apply --yes --allow-album-deletion [--allow-file-deletion]` → checksum/origin/history/claim gates → preflight (missing==satisfied, drift fail-closed) → strictly sequential per-entry: fresh re-read → `deleteAlbum` dispatch → not-found==satisfied / retryable==deferred → bounded absence verification → JSONL history → resume/deferred replay idempotent by construction.

### Implementation phases

P1 primitives (types/projections + client mutations + resilience + contract pins + arch-gate ownership; album-scan/album-selection extraction with plan-albums regression) → P2 `albums` read leaf → P3 delete lane (plan types → plan-album-operations → producer → apply integration + verification → presenter → command/flags) → P4 `album-edit` (severable) → P5 completions + docs + ROADMAP + validation.

## 6. Safety model

1. **Sealed plan/apply only** — no direct-mutation delete/edit command exists; plus a CI-structural guarantee: the architecture gate makes `deleteAlbum`/`setAlbumAnyReleaseOk` uncallable outside plan-album-operations.ts + resilience.ts.
2. **Two-key destructive authorization** — `--allow-album-deletion` for any real album-delete apply; `--allow-file-deletion` additionally when the SEALED plan carries deleteFiles=true (destruction mode decided at plan time, not escalatable at apply). Enforced at command AND action layers; `--yes` is approval only and never substitutes; dry-run needs neither so review is frictionless; interactive path keeps dry-run-review → labeled confirm.
3. **Blast-radius control at plan time** — selector-mode delete requires explicit `--artist-ids` (no `--all`); monitored albums excluded by default (`--include-monitored`, exclusions counted); per-entry trackFileCount/sizeOnDisk sealed into before-state; maxBatch default 25 / cap 1000 / 1000-entry cap with narrow-hints; never a silently partial plan (any failed/skipped scan task aborts before write).
4. **Wrong-target protection** — foreignAlbumId + monitored captured at plan time; preflight and per-entry admission classify mismatches as drifted → blocked-stale, nothing dispatched.
5. **Idempotent deletion under flakiness** — per-operation missing-target==satisfied at preflight, admission, resume, and deferred replay; dispatch/replay not-found (via existing `isNotFound`) → satisfied. The client does NOT swallow 404 (fail-fast at the boundary); idempotency semantics live in the definition/apply layer with history evidence. Deferred intents carry exact payloads keyed by sha256 idempotencyKey, revalidated (exact-key/sensitive-key) before replay. `deleteAlbum` is retry-DENIED in place — retryable failures defer, never hot-retry a destructive call.
6. **Verified destruction** — bounded post-dispatch absence verification (existing reconciliation constants); still-present → "failed" with structured failure evidence; transient verify error → "uncertain". No false success on the destructive lane (closing, for the new kinds, the v1 album path's no-verification gap). History-write failure after remote success → "uncertain" + stopAdmissions (unchanged invariant).
7. **Edit clobber guardrail** — the GET→mutate-one-field→PUT round-trip is confined to one client method and contract-tested to preserve unprojected wire fields verbatim.
8. **Inherited engine guarantees** — exact-allowlist untrusted-JSON validation, checksum + expected-plan-id/checksum pinning, origin match, exclusive per-plan claim lock, strictly sequential execution, per-plan JSONL history, resume, exit code 1 on partial/failed, stderr/stdout parity, reportLidarrFailure redaction with sensitiveValues.

## 7. Pagination / large-library reliability

The whole-library client scope guard (client.ts:570-576) is never weakened: `lidarr albums --all` and all plan scans iterate per-artist (each response bounded under the 8 MiB transport cap; explicit-ID reads chunked at 200/GET per LIDARR_ALBUM_IDS_CHUNK_SIZE) through the fail-closed scheduler batch with progress every 100 artists. Presentation paging is client-side limit/offset over a deterministic (artistId, albumId) sort — stable windows, honest `total`/`returned` accounting, no silently truncated listing (any partial batch aborts). No server paging is advertised because GET /api/v1/album has none (types.gen.ts:1710-1729). No album caching / `--allow-stale` (deliberate; metadata-cache.ts:19).

## 10. Rejected alternatives (decided)

- **v1-lane extension for edit/delete (P1)** — the v1 interface hard-codes monitoring shapes end-to-end (plan-engine.ts:211-265; validator :1053-1128; review.changed invariant :1196-1220); delete entries without before/after break its structural assumptions; refactoring the frozen lane risks pinned checksums and forfeits sealed selection + structured failure evidence exactly where the first destructive operation needs them.
- **v2 genericization to definition-owned identity (P2)** — requires changing the LidarrArtist-typed classify/verify signatures across all three shipped artist definitions plus buildLidarrMutationPlanV2/requireEntryIdentity; largest blast radius on the highest-assurance pinned code for zero user-visible gain over the parallel album-typed definition (which the codebase already precedents via the v1 album definition and apply's definition-shape union).
- **Client-side 404 swallowing in deleteAlbum (P1)** — hides real failures at the boundary (violates fail-fast); already-deleted semantics belong to the definition/apply layer (existing `isNotFound` helper) where they are recorded as outcome "satisfied" with history evidence.
- **No post-dispatch verification for delete (P1's accepted trade-off)** — rejected; file destruction gets bounded absence verification; the reconciliation machinery and constants already exist.
- **Single authorization flag covering file deletion (P1)** — a sealed plan can be applied later by a script that never saw the plan flags; on-disk destruction gets its own apply-time acknowledgment (--allow-file-deletion, reusable by #200).
- **Direct-mutation `lidarr albums delete/edit` commands** — violates the sealed-mutation contract (PR #259) and bypasses claim/history/resume/drift guardrails.
- **`lidarr list --albums` mode flag / `lidarr albums list` noun nesting / renaming `list` to `artists`** — breaks per-leaf CSV+completion contracts, contradicts the flat-leaf lidarr namespace, or is a gratuitous breaking change.
- **Weakening the unscoped GET /api/v1/album guard; wanted-style server paging for albums** — endpoint is unpaginated; large libraries would trip the 8 MiB transport cap; per-artist iteration is the only honest bounded path; advertising server paging would be a lie.
- **--sort-key/--sort-dir on `lidarr albums` (P2)** — inflates the exact-set completion contract and test surface for a read leaf; a fixed deterministic (artistId, albumId) sort delivers the actual requirement (stable pagination). Revisit on user demand.
- **New getAlbum(albumId) facade method** — `listAlbums({albumIds})` already provides targeted bounded reads AND makes absence observable without error handling; a new method would need resilience wiring + retry-allowlisting + contract pins for no capability gain.
- **Album metadata-cache category / --allow-stale for albums** — page-explosion (same reason wanted is uncached); stale destructive-adjacent data is worse than a failed read.
- **Kind-discriminant field on plan entries** — exact-allowlist validators forbid new keys on existing shapes; new shapes are provably key-disjoint and per-plan homogeneous via operation.kind.
- **POST /api/v1/albumstudio for edit** — couples artist/album monitoring semantics, unpinned, offers no anyReleaseOk control.
- **Typed plan-id confirmation ritual for file deletion** — layered consent (two flags + sealed plan + review + confirm) already provides the machine-checkable guarantees; a typing ritual adds friction only.
